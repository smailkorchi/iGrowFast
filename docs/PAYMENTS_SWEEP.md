## 1. Executive Summary

The system pays two collaborator classes from one commission base:

- **Sellers (`role='commercial'`)** — a **rolling monthly ledger**. Each `(seller, business, month)` is a *ticket*. Unpaid balance carries forward month-to-month (`carried_out → next carried_in`). Commission accrues live in the `seller_daily_earnings` view (per delivered order, flat or per-unit). Two crons maintain tickets: hourly `refresh_open_seller_ticket` (re-syncs current-month earnings) and monthly `close_seller_month` (freezes the prior month, rolls the balance). The **only** sanctioned write path is the `pay_seller` SECDEF RPC.
- **Media buyers (`role='mediabuyer'`)** — **independent monthly rows**, no carry, no cron, no ledger view. Earnings computed entirely client-side (`useMediaBuyerEarnings`) from `campaign_daily_entries` + `orders`. Payouts generated by direct UPSERT; payments by direct txn insert.

Both classes use the same partial-payment substructure: a parent `*_payments` row + append-only `*_payment_txns` children; a trigger keeps `paid_amount = Σ txns` and derives `status`.

4. Two unguarded, publicly-executable SECDEF functions exist (G2).

## 5. Calculations & Edge Cases

### 5.1 Seller commission (atomic accrual)
- **per_order** (default; `commission_basis` NULL/≠`per_unit`): `commission = commission_price` (flat per delivered order).
- **per_unit**: `commission = commission_price × sum_order_units_for_seller_products(order, seller)`.
- Empty `users.products` → 0 units → 0 commission (client mirror matches). `commission_price` NULL → 0. `quantity ≤ 0` excluded (returns not subtracted).

### 5.2 View bucketing (`seller_daily_earnings`)
- Day = `COALESCE(date_livraison, updated_at)`. Inclusion = all four predicate clauses.
- **Re-bucketing:** any update to a delivered order with NULL `date_livraison` jumps its bucket on every touch. **But** `set_order_date_livraison_on_delivery` stamps `date_livraison` on first delivered transition (G4) → for normally-delivered orders the bucket is frozen; the every-touch hazard only hits orders that reached `category='delivered'` via a status path whose label doesn't match `%livr%/%deliver%`. Narrow but real.
- `source_review_status` flips off `pending` → order enters view → adds to current open ticket retroactively for its delivery day.

### 5.3 Rolling ledger
- Invariants: `total_amount = carried_in + month_earned` (CHECK); `remaining = total − paid` (can be negative); `paid_amount = Σtxn` (trigger); `owe = open.remaining`.
- `refresh_open_seller_ticket`: recomputes `month_earned/commission_earned/delivered_orders/total_amount` for OPEN tickets only, guarded by `month_earned IS DISTINCT FROM v_earned` (idempotent). Closed tickets never touched (`earned_frozen`).
- `close_seller_month`: per (seller,biz) advisory-locked; freezes prior month (`carried_out = total − paid`), opens next month with `carried_in = carried_out`. Idempotent for target month; **does not backfill gaps (G8)**. Fully-zero open tickets (0/0/0) are skipped and persist stale.
- `pay_seller`: finds/creates open ticket (carry from latest closed `carried_out`), calls `refresh_open_seller_ticket`, inserts ONE txn. **No FIFO at DB level** — lump txn against open ticket; "FIFO/carry" is at the month grain. **No upper bound** → overpay allowed.
- Status derivation: `paid≤0→pending`; `paid≥total AND total>0→paid`; else `partial`. `total=0` with `paid>0` → **`partial` forever**.

### 5.4 Edge cases — seller
| Case | Behaviour | Cleanup hazard |
|---|---|---|
| Overpay zero-earned month | `total=0, paid>0 → carried_out<0`, rolls forward as negative `carried_in` credit | **This is G1, live now (−280).** "Zero negative tickets" erases over-disbursement evidence. |
| Rate change mid-month | open re-prices (hourly/at-pay); closed frozen | Editing rate retroactively changes all open-month earnings. |
| No open ticket exists | live owe still shows (view-based); `pay_seller` recreates with carry | Don't assume an open ticket row exists. |
| Delete closed ticket | breaks carry chain silently (CHECK still satisfied locally) | `close_seller_month` will NOT rebuild deleted history. |
| Product/seller reassignment | view groups by current `orders.seller_id` → commission moves between sellers retroactively (G4) | Touching `users.products`/attribution triggers re-attributes past earnings. |
| Refund | impossible (CHECK amount>0); only via txn DELETE | Negative carry is the only legit negative path. |

### 5.5 Media buyer
- **Salary:** `commission_earned=0, salary_earned=total_amount=salary_amount` regardless of activity.
- **Commission:** distinct `(entry_date, source)` pairs → `delivered × commission_price`. **Globally bucketed: two MBs on same source+day BOTH get full count — no division (by design double-count).** Orders widened ±1 day for UTC/local skew, re-bucketed client-side.
- `prior_paid_amount = Σ total_amount` (NOT `paid_amount`) → **generated-but-unpaid shows remaining=0, masks unpaid MB (G10)**.
- UNIQUE without business → cross-business UPSERT clobber (C5).
- No carry; each month independent; `paid_amount = Σtxn`.

### 5.6 G6 — silent zero-commission class
Orders with `source_name='whatsapp'` OR `source_review_status='pending'` get NO `seller_id` from `auto_attribute_order` → excluded from view (requires `seller_id IS NOT NULL`). Approved-from-pending orders can permanently lack a seller and never accrue commission.
